01 · Scope

What SangamID holds — and what it doesn't

Scope discipline is the single most important design rule. Every future feature request must pass one test: "Does every partner app need this?" If just one, it belongs in that app — not in SangamID.

✓ SangamID Holds

✓
User identity
One User = one identity across every app and org. Email is the natural key. Credentials, name, phone, verification status, MFA state.
✓
Organisations (tenants)
Clinics, hospitals, construction firms, labs — any real-world entity users belong to. Type-classified, metadata-rich, cross-app.
✓
Memberships & roles
Which user belongs to which org, with which role, in the context of which app. The same person can be admin in LiPi and viewer in Apollo HIS for the same clinic.
✓
Partner app registry
Registered OIDC clients — LiPi, Apollo HIS, Compliance app. Client secrets, redirect URIs, allowed scopes, per-app roles.
✓
Consent records
Explicit, versioned, timestamped. Which user consented to which app, for what data, at which policy version. DPDPA-defensible by design.
✓
Audit trail
Every identity event — login, registration, consent, membership change, admin action — append-only, retained per regulatory requirement.
✓
Sessions & tokens
Active login sessions, OIDC/OAuth 2 tokens, refresh tokens with rotation, JWKS with rotating keys.

✗ SangamID Does NOT Hold

✗
Clinical or domain data
Patient records, treatment plans, dosimetry, scans — all live in LiPi / HIS / their own databases, keyed by the SangamID user ID.
✗
Payment or billing info
Each partner app handles its own subscriptions, invoices, customer billing. The platform doesn't touch money.
✗
App-specific settings
UI preferences, notification rules, workflow configurations belong to each app's own database — not to shared identity.
✗
Business documents
Contracts, agreements, quotes, reports live in the partner apps that own those workflows. SangamID is identity plumbing only.
✗
Communications
Email between users, chat messages, notifications beyond identity events — all in the apps that own those relationships.
✗
App-level permissions logic
SangamID stores roles; it doesn't enforce what a "doctor" role can do inside LiPi. That authorisation logic lives in each app.
✗
Any commercial activity
The platform never sells, markets, or bills. Every commercial relationship is between the user and a specific partner app.
02 · Features (v0)

What ships in the first 90 days

The minimum viable set for one partner app to run in production. Every item below is scoped, planned, and included in the v0 sprint plan.

Registration & email verification
Email + password with rate limiting, CAPTCHA (Cloudflare Turnstile), verification via emailed link, resend flow.
Login & session management
Argon2id hashing, account lockout on failed attempts, sliding-expiry sessions, "log out everywhere" support.
Full OIDC / OAuth 2 server
Authorization Code with PKCE, refresh token rotation, DPoP, JWKS with rotating keys, discovery endpoint, token introspection.
Password reset
Time-limited emailed link, single-use tokens, session invalidation on password change via security stamp rotation.
Organisation management
Create, edit, classify by type (clinic, hospital, lab, construction firm). Metadata-flexible via JSONB. Add/remove members.
Consent management
First-time consent screen naming the specific app and specific data. Versioned. Self-service revocation. Re-consent when policy changes.
Admin UI (Blazor)
Operator dashboard with MFA-mandatory access. User search, org management, app registration, secret rotation, audit log viewer.
Self-service portal (Blazor)
Users manage profile, view/revoke linked apps, see sessions, export their data (DPDPA), delete account with cascade.
Append-only audit log
Every identity event captured. Actor, action, target, IP, user-agent, timestamp. Immutable via DB-level rules. Searchable in admin UI.
Role model per (User, Org, App)
Roles scoped to the (user, org, app) triple. Same person can hold different roles in the same org across different apps.
NuGet SDK (Sangam.Client)
Partner apps integrate in ~10 lines of code. Thin wrapper over OIDC middleware with helpful extensions (.GetOrgs(), .HasRoleInOrg()).
DPDPA rights, self-service
Right to access (data export within 30 days), right to correction, right to erasure, right to withdraw consent — all buttons in the portal.
03 · Data model

The eight core entities

These are the load-bearing entities of the platform. Get them right and the platform flexes gracefully as partners, features, and use cases grow. Every other data structure sits on top of these.

User
One human = one row. Ever. Email is the natural key.
id email name status mfa
Organisation
A real-world entity users belong to. Clinic, firm, department.
id name org_type metadata
App
A registered partner application. OIDC client.
id client_id redirect_uris scopes
OrgMembership
The core relationship. User × Org × App × Role.
user_id org_id app_id role_id
Role
A named capability set defined by each App.
app_id code permissions
Consent
User's explicit, versioned permission for an App.
user_id app_id version granted_at
Session
An active login. Device, IP, sliding expiry.
user_id device expires_at
AuditEvent
Append-only record of every significant action.
actor action target timestamp
04 · Public API

The OIDC endpoints partner apps talk to

Every partner app — LiPi, Apollo HIS, Compliance app — interacts with SangamID through these standard OIDC endpoints. Nothing custom, nothing proprietary. Full standards compliance means partner apps can switch identity providers if ever needed.

GET
/.well-known/openid-configuration
Discovery document listing all endpoints and capabilities
GET
/authorize
Start the login flow — user redirected here from partner app
POST
/token
Exchange authorization code for tokens; refresh token rotation
GET
/userinfo
Retrieve user's claims — orgs, roles, permissions
GET
/jwks
Public signing keys for verifying tokens; rotates automatically
POST
/introspect
Server-to-server token validation (RFC 7662)
POST
/revoke
Revoke a token before its natural expiry (RFC 7009)
GET
/logout
End the SangamID session, redirect back to partner app
